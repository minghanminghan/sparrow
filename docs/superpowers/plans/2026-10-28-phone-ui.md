# Phone UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An installable sparrow PWA that opens on the board with no signal, loads little data, and queues new tasks (with photos) offline without duplicates.

**Architecture:** Same Next.js app, responsive below `md` (768px). Server gains idempotent create (`clientId`) and an index revision (`rev`) used for ETag/304 and to skip unchanged SSE snapshots. Client caches the last index in IndexedDB, keeps an outbox for creates made offline, and a hand-written service worker caches the app shell.

**Tech Stack:** Next.js 16 app router, React 19, zustand 5, Tailwind v4, vitest (node env), `idb-keyval` (new, only new dependency), `node:sqlite`.

**Spec:** `docs/superpowers/specs/2026-10-28-phone-ui-design.md`

## Global Constraints

- Button copy on the new-task screen is exactly "Cancel", "New task", "Create" (never "Post"). Bottom bar copy: "+ New task". Pending label: "Waiting to send". Offline bar: "Offline · tasks from <age> ago".
- Reuse existing components and Tailwind classes (gray palette, white cards, `bg-gray-900` primary). No separate mobile theme or fork.
- Phone layout applies below `md`; desktop (`md` and up) must look and behave as today.
- When online, "Create" waits for the server and shows server errors as a toast, as today. The outbox is used only when offline or when the request fails on the network / times out.
- A retried create must never make a second task.
- iOS Safari is the target. No background sending; flush when the app is open or returns to the foreground with a connection.
- `/tasks` ("All tasks") stays desktop-only: no phone layout, no offline requirement.
- No sign-in. Works at `https://andrewsserver.tail39014e.ts.net:8443`.
- Conventional commits; PR title follows the same format (`feat(ui): ...`).

## Review Focus

1. Create tapped twice, or retried after a lost response → exactly one task (Task 1 test `createTask with the same clientId returns the first task`; Task 4 test `flush retries with the same clientId`).
2. Weak signal where `fetch` hangs instead of failing → the create is queued after the timeout, the screen closes, no endless spinner (Task 4 test `create queues after CREATE_TIMEOUT_MS`).
3. App reopened after a deploy → cached index from another major version is discarded; service worker serves the new shell on the following open (Task 3 test `loadCachedIndex ignores a different major version`; Task 7 verification step).
4. A queued create the server rejects (4xx, e.g. parent deleted) → stays visible with the error and Retry/Discard, never silently dropped (Task 4 test `flush marks a 4xx as error and keeps it`).
5. iPhone home indicator and on-screen keyboard → the "+ New task" bar and the "Create" button stay visible and tappable (Task 6 verification step with `env(safe-area-inset-bottom)` and 390×844 viewport).

**Files:**

**Interfaces:**
- Consumes: `CreateInput.clientId` (Task 1); `connected` (Task 3).
- Produces in `outbox.ts`:
  - `type OutboxEntry = { clientId: string; input: CreateInput; photos: { name: string; blob: Blob }[]; createdAt: number; taskId?: string; error?: string }`
  - `CREATE_TIMEOUT_MS = 8000`
  - `type OutboxDeps = { createTask(input: CreateInput, signal: AbortSignal): Promise<TaskView>; uploadAttachment(id: string, file: File): Promise<TaskView> }`
  - `flushEntry(e: OutboxEntry, deps: OutboxDeps): Promise<{ entry: OutboxEntry | null; task?: TaskView }>` — `null` entry means done.
  - `isNetworkError(err: unknown): boolean` — true for `TypeError` from `fetch` and `AbortError`/`TimeoutError`; false for `ApiError`.
  - `loadOutbox(): Promise<OutboxEntry[]>`, `saveOutbox(entries: OutboxEntry[]): Promise<void>` (idb-keyval key `'outbox'`).
- Produces in the store: `pending: OutboxEntry[]`; `create(input: CreateInput, photos?: File[]): Promise<TaskView | null>` (`null` = queued); `retryPending(clientId: string): Promise<void>`; `discardPending(clientId: string): Promise<void>`; `flushOutbox(): Promise<void>`.

- [ ] **Step 1: Write the failing tests** in `src/client/outbox.test.ts` with fake `OutboxDeps`:
  - `flush creates the task, uploads photos, and finishes` → `entry === null`, upload called once per photo with the returned task id.
  - `flush retries with the same clientId`: first `createTask` rejects with `new TypeError('Load failed')` → entry kept, no `error`; second call receives the same `clientId`.
  - `flush keeps taskId when a photo upload fails on the network` → returned entry has `taskId`, and the next flush does not call `createTask` again.
  - `flush marks a 4xx as error and keeps it`: `createTask` rejects with `new ApiError('not_found', 'task 9 not found')` → entry kept with `error === 'task 9 not found'`.
  - `create queues after CREATE_TIMEOUT_MS`: `createTask` never resolves; with fake timers, after `CREATE_TIMEOUT_MS` `flushEntry` resolves with the entry kept and no `error`.
- [ ] **Step 2: Run** `pnpm test src/client/outbox.test.ts` → FAIL.
- [ ] **Step 3: Implement `outbox.ts`** (`AbortSignal.timeout(CREATE_TIMEOUT_MS)` for the create).
- [ ] **Step 4: Implement the store.** `create`: give every create a `crypto.randomUUID()` `clientId`. If `!connected`, queue at once and return `null`. Else call the API with the timeout; on success behave as today (also upload `photos`); on `isNetworkError` queue and return `null`; on `ApiError` toast and throw as today. Queued entries go to `pending` and `saveOutbox`. `connect()` loads the outbox. Flush (one at a time, entries in order) on SSE `onopen` and on `visibilitychange` to visible while `connected`. A flushed task is merged into `index`/`byId` like today's create.
